# 附录 C 学习路线与资源

> **本章目标**：把前面 44 章的内容重新组织成一条有先后、有验收标准的学习路径；指出最常见的八种走弯路的方式；给出一份可以直接照着执行的 14 周日程；并说明遇到问题时该去哪里找答案。

## C.1 Rust 的五道关

学 Rust 的困难不是均匀分布的，而是集中在几个明确的关卡上。知道自己在第几关，比「读完多少页」有用得多。

| 关卡 | 核心问题 | 典型症状 | 大致耗时 |
| --- | --- | --- | --- |
| 一、语法关 | 能读懂代码 | 看得懂示例，自己写就卡 | 1–2 周 |
| 二、所有权关 | 能通过借用检查 | 改十行代码，编译报二十个错 | 2–4 周 |
| 三、抽象关 | 会用泛型与 trait 建模 | 到处 clone，或者写不出通用函数 | 3–4 周 |
| 四、并发关 | 能安全地并发 | 卡在 Send/Sync、生命周期跨线程 | 3–4 周 |
| 五、工程关 | 能交付可维护的项目 | 能写但不敢重构，测试与错误处理混乱 | 持续 |

一个重要的心理准备：**第二关会让很多人误以为自己不适合 Rust**。事实上那是学习曲线最陡的一段，跨过去之后（通常是第一次独立写出一个不需要 `clone()` 兜底的程序），后面的路反而平缓。

## C.2 阶段一：语法关

**目标**：能读懂官方书前 10 章的任何示例，能独立写出 100 行以内的小程序。

**要掌握的东西**：变量与可变性、基本类型、函数与控制流、结构体与枚举、`match`、`Option`/`Result` 的基本用法、模块与 `use`、`Vec`/`String`/`HashMap` 的常用方法。

**怎么练**：这一阶段不要纠结所有权细节，遇到 `cannot move out of borrowed content` 就先 `clone()`——后面会回来清理。重点是让手熟悉语法。

**验收标准**（能全部做到就算过关）：

1. 不查资料写出一个读取命令行参数、统计词频并按次数排序输出的程序。
2. 解释 `String` 与 `&str` 的区别，并说明什么时候该用哪个。
3. 用 `enum` 定义一个「表达式树」并写 `eval` 函数（第 9 章的练习）。
4. 说清楚 `let mut x` 里 `mut` 修饰的是绑定还是值。

## C.3 阶段二：所有权关

**目标**：不再靠 `clone()` 绕过借用检查，能读懂并修复 E0382、E0502、E0499、E0597 这四类错误。

**要掌握的东西**：移动语义、`Copy` 与 `Clone`、借用规则（共享 XOR 可变）、生命周期标注的基本用法、切片与字符串边界、`&mut` 的重借用、NLL。

**怎么练**：找一个自己以前用别的语言写过的小工具（比如日志过滤、CSV 转换），用 Rust 重写，**强制要求：不出现不必要的 `clone()`**。每写一次 `clone()`，停下来问自己「真的需要复制吗，还是可以借」。

**验收标准**：

1. 能解释为什么 `fn f(v: Vec<i32>) -> Vec<i32>` 调用后原变量不可用，而 `fn g(v: &Vec<i32>)` 可以。
2. 能手写 `split_at_mut` 的安全版本，或者说明为什么安全版本需要额外工作。
3. 看到 `error[E0597]: ... does not live long enough` 时，能定位是哪个临时值提前销毁。
4. 能说清楚「返回引用」什么时候必须标注生命周期。

## C.4 阶段三：抽象关

**目标**：能用泛型和 trait 建模，能判断什么时候该用 `dyn`、什么时候该用泛型参数。

**要掌握的东西**：泛型函数与泛型结构体、trait 定义与实现、默认方法、关联类型、trait 约束与 `where`、`impl Trait`、trait 对象与对象安全、运算符重载、`From`/`Into`/`TryFrom` 的转换体系。

**怎么练**：写一个「通用缓存」：支持容量上限、淘汰策略（LRU / FIFO 二选一，用 trait 抽象）、键值任意类型（用泛型约束）。这个练习会把 trait 约束、关联类型、所有权三件事同时压上来。

**验收标准**：

1. 能说明 `fn f<T: Display>(x: T)` 与 `fn f(x: &dyn Display)` 在编译产物与调用方式上的差别。
2. 能判断一个 trait 是否对象安全，并说明原因。
3. 能给一个类型实现 `From<A> for B` 后直接使用 `Into`，并解释为什么不要手写 `Into`。
4. 能读懂 `impl<T: ?Sized> Trait for &T` 这类标准库签名。

## C.5 阶段四：并发关

**目标**：能用线程与通道写出正确程序；能判断一段异步代码会不会卡住运行时。

**要掌握的东西**：`thread::spawn` 与 `move`、`Arc<Mutex<T>>`、通道（mpsc / sync_channel）、`Send`/`Sync` 的含义、原子类型与内存序的基本直觉、`async`/`await` 与 Future 的惰性、tokio 的任务与 `spawn_blocking`。

**怎么练**：写一个并发下载器（或并发文件处理器）：N 个工作线程、一个任务队列、主线程汇总结果、支持优雅退出。然后再用 tokio 重写一遍，对比代码结构差异。

**验收标准**：

1. 能解释为什么 `Rc<T>` 不能跨线程，而 `Arc<T>` 可以；为什么 `Arc<RefCell<T>>` 仍然不行。
2. 能写出不会死锁的「两个锁」场景（固定加锁顺序或合并成一个锁）。
3. 能解释「async fn 是惰性的，不 await 就不执行」。
4. 能说出在 async 代码里调用 `std::thread::sleep` 会有什么后果。

## C.6 阶段五：工程关

**目标**：交付一个别人能接手维护的项目。

**要掌握的东西**：模块划分与可见性、错误类型设计、测试分层（单元/集成/文档测试）、日志与追踪、格式化与 clippy、CI、文档注释、发布流程。

**怎么练**：把前面任何一个练习升级成「可发布」状态：加 README、加 CI、加覆盖率、加 `#![deny(missing_docs)]`、发到 crates.io（或至少 `cargo publish --dry-run` 通过）。

**验收标准**：

1. 新同事能只读 `lib.rs` 的公开 API 与文档，就知道怎么用你的库。
2. `cargo clippy -- -D warnings` 与 `cargo fmt --check` 都干净。
3. 错误信息能让用户知道「发生了什么、该怎么办」。
4. 关键路径有测试覆盖，重构时敢动手。

## C.8 八个常见误区

**误区一：先把语法全部学完再写代码。**
结果通常是学完就忘。正确顺序是「学够写出一个小程序 → 写 → 卡住 → 回去查」。每一章都配一个能跑的东西，比读完十章的收获大。

**误区二：一上来就读 unsafe 和宏。**
这两块是「知道边界之后才能安全使用」的知识。没有项目经验时读，只会记住一堆语法而不知道为什么要这样。它们适合放在第五关之后。

**误区三：用 `clone()` 绕过所有借用错误。**
短期有效，长期有害：你会一直不知道借用检查器想告诉你什么，性能也会悄悄变差。可以暂时用，但每次都要回头问「能不能不克隆」。

**误区四：把 Rust 当 C++/Java 写。**
典型表现是用大量 `Rc<RefCell<T>>` 模拟对象图、到处显式指定类型、用继承式思维设计 trait 层级。Rust 的惯用法是：数据与行为分离、用枚举表达状态、用所有权表达生命周期，而不是用引用计数模拟 GC。

**误区五：只读不写，或只写不读。**
只读不写会形成「看得懂但写不出」的假象；只写不读会在错误的方向上重复几百次。比较合理的比例是读一小时、写两小时，并且写的东西要能跑出结果。

**误区六：追求「零 clone、零 unsafe、零 unwrap」。**
三个都是手段不是目标。库的边界处用一次 `unsafe` 把复杂性关起来，比在全项目里散布「看起来安全」的变通写法更好；原型阶段大量 `unwrap` 也完全正常，只是交付前要清理关键路径。

**误区七：不着手用编译器给的帮助。**
Rust 的错误信息是整个生态最宝贵的资产：它有错误码、有 `help:` 建议、有 `note:` 解释。看到 `help: consider borrowing here` 就直接照着改，看到错误码就 `rustc --explain E0382`（或用 `cargo explain` 类工具）。**不要一眼扫过去然后去搜索引擎找答案**——编译器说的通常比搜索结果更贴合你的代码。

**误区八：不敢重构。**
有了类型系统和测试之后，重构 Rust 代码的成本比多数语言低。函数签名一改，所有调用点会一起报错；这正是类型系统的价值所在。把「改完编译通过」当成一次免费的全面检查。

## C.9 怎么读源码和文档

### C.9.1 文档的正确打开方式

`docs.rs` 是阅读任何一个 crate 的首选入口。看一个库的顺序：

1. **先读 crate 级文档**（首页那段文字）。好的库会在首页给出「三十秒上手」示例与主要概念的关系。
2. **再看有哪些 feature**。知道默认打开了什么，避免莫名其妙拖进一堆依赖。
3. **看主要类型的公开方法列表**。先看 `new`/`from` 这类构造入口，再看变换方法，最后看终结方法。
4. **重点看每个方法的「Panics」「Errors」「Safety」小节**。这是 API 契约的精华：什么情况下会 panic、什么时候返回 Err、什么前提必须由你保证。
5. **最后才点进源码**。很多时候方法文档里的示例比源码更省时间。

本地查文档用：

```bash
cargo doc --open --no-deps        # 只文档本项目
cargo doc --open                  # 含所有依赖
```

### C.9.2 读标准库源码

标准库源码是学习惯用法的宝库，但直接读 `Vec` 的实现会撞上大量 `unsafe`，容易被劝退。推荐的阅读顺序是从「小而完整」的模块开始：

| 模块 | 能学到什么 |
| --- | --- |
| core::option / core::result | 组合子方法怎么写、文档注释格式 |
| core::iter::adapters | 迭代器适配器的实现套路 |
| alloc::string | UTF-8 与字符串 API 的设计 |
| std::sync::mpsc | 通道的内部结构（锁 + 条件变量） |
| std::collections::hash_map | 哈希表、SipHash、entry API |
| core::slice | 切片边界处理与 unsafe 的封装方式 |

读的时候有一个固定问题要问自己：**「这个 API 为什么是这样设计的，如果换成别的方式会有什么问题？」** 例如 `Vec::get` 返回 `Option<&T>` 而不是 panic，是为了让调用方选择处理方式；`[T]::sort_unstable` 与 `sort` 并存，是为了把「稳定性」这个成本交给调用方决定。

### C.9.3 读第三方 crate 源码

挑一个「体积小、质量高、你正在用」的 crate，比如 `once_cell`、`semver`、`tempfile`。方法是：

1. 先看 `lib.rs` 顶部的文档与 `pub use` 布局，理解它的模块划分。
2. 挑一个你用过的方法，从公开签名追到实现，看它的边界处理。
3. 搜索 `unsafe`，看它在什么地方用了、`SAFETY` 注释怎么写。
4. 看它的测试组织和错误类型设计。

## C.11 自检清单

读完本书后，用下面 20 个问题测一下自己。能答出 15 个以上，说明基础已经扎实。

1. `let x = 5; let y = x;` 之后 `x` 还能用吗？换成 `String` 呢？为什么？
2. `&T` 与 `&mut T` 能同时存在吗？为什么这样规定？
3. 为什么 `fn first(v: &Vec<i32>) -> &i32` 不需要写生命周期，而返回两个引用之一就需要？
4. `Option<&u8>` 和 `&u8` 大小一样吗？为什么？
5. `#[repr(C)]` 与默认布局在多字段结构体上有什么实际差别？
6. 什么时候该用 `&str`，什么时候该用 `String`？
7. `Box<dyn Error>` 与自定义错误枚举各自的适用场景是什么？
8. `impl Trait` 作为参数与作为返回值，语义有什么不同？
9. 什么 trait 不能用作 `dyn`？举两个原因。
10. `Rc<T>` 与 `Arc<T>` 的区别是什么？为什么 `Arc<RefCell<T>>` 不能跨线程？
11. `Mutex` 中毒是什么？如何正确处理？
12. 原子操作的 `Relaxed` 与 `SeqCst` 差在哪？
13. `async fn` 返回什么？不 `.await` 会执行吗？
14. 为什么在异步任务里做阻塞 IO 会拖垮整个运行时？
15. `Send` 与 `Sync` 分别保证什么？
16. 单元测试与集成测试的区别是什么？集成测试只能访问什么？
17. `#[non_exhaustive]` 的作用是什么？代价是什么？
18. `macro_rules!` 里的 `$x:expr` 与 `$x:tt` 有什么差别？
19. 什么是未定义行为？为什么不能「靠经验知道它实际能用」？
20. 一个库的公开 API 改了以后，为什么是破坏性变更？

## C.12 小结

- 学习路径分成语法、所有权、抽象、并发、工程五关，难度集中在第二关，知道自己在哪一关比追求阅读量重要。
- 每一关都要有可运行的产出与明确的验收标准，只看不写是最常见的失败模式。
- 借用检查器的报错是学习工具而不是敌人；错误码与 `help:` 建议应该优先于搜索引擎。
- 不要在语法期碰 unsafe 与宏；它们需要项目经验作为背景。
- 用 `clone()` 兜底是允许的临时手段，但要养成每次回头检查的习惯。
- 读文档的顺序是：crate 首页 → feature → 类型方法列表 → Panics/Errors/Safety 小节 → 最后才源码。
- 读标准库从 `Option`/`Result`/迭代器开始，别从 `Vec` 的 unsafe 实现开始。
- 挑一个正在用的小 crate 完整读一遍，对 API 设计能力的提升比读三个大 crate 更大。
- 最后用 20 条自检清单检验自己，答不出的条目对应回本书的具体章节补课。
